HTTP→MCP Method-Inference Soundness

What can a translator safely promise about an MCP tool when all it knows is that the source operation was GET, POST, PUT, PATCH, or DELETE?

Core result: an HTTP method gives a translator a limited semantic claim budget. Under the profile's effect-faithful translation assumption, GET can justify a read-only claim, PUT and DELETE can justify idempotence, while POST and PATCH justify no positive Core guarantee from the method alone. The executable oracle checks every covered method against every combination of the three MCP annotations, 40 states in total.

The problem in plain language

Turning an API operation into an agent-facing tool often involves filling in metadata about what that tool can do. MCP exposes hints such as readOnlyHint, destructiveHint, and idempotentHint. Those hints can shape how another system plans, approves, or repeats an action.

The tempting shortcut is to infer those properties from the HTTP method. Some inferences are well grounded. Others quietly say more than the method actually guarantees.

A GET request has standardized safety semantics, so a faithful translation has a real basis for a read-only claim. PUT and DELETE are standardized as idempotent, so idempotence can be carried across under the profile's repetition assumptions. But POST does not generically mean "additive only," and PATCH does not generically mean "non-destructive" or "idempotent." A translator that invents those stronger properties has crossed from translation into unsupported semantic gain.

The five-method claim budget

The Core is intentionally small. It asks only what follows from the standardized method semantics of GET, POST, PUT, PATCH, and DELETE, using RFC 9110 and RFC 5789 as the source basis.

HTTP method What the method alone can justify in this profile GET READ_ONLY, ADDITIVE_ONLY, IDEMPOTENT POST no positive Core guarantee PUT IDEMPOTENT PATCH no positive Core guarantee DELETE IDEMPOTENT

For GET, the profile treats read-only as also satisfying its additive-only and idempotent guarantees at the requested-effect level. In the actual MCP encoding, readOnlyHint=true is the maximal representation and the dependent raw hints become semantically inactive.

One rule drives the checker

The profile separates what the source method justifies from what the generated MCP annotations actively claim. Soundness is then a simple containment question.

SOUND iff ActiveGuarantees(annotation state) ⊆ JustifiedGuarantees(HTTP method)

This matters because the checker does not punish caution. A translator may say less than it could safely say and still be sound. The failure condition is the opposite: asserting an active guarantee that has no basis in the source method.

Why there are 40 states

The Core covers five HTTP methods. Each generated MCP tool can resolve the three covered annotation fields to eight boolean combinations. Five methods times eight annotation states gives an exhaustive 40-state oracle.

A few concrete examples

GET marked read-only

Assuming the generated tool faithfully represents the GET operation's requested effect, readOnlyHint=true is supported. This is the profile-maximal GET representation.

POST marked non-destructive

When a non-read-only tool sets destructiveHint=false, the profile reads that as an active additive-only guarantee. POST semantics do not justify that guarantee in general, so a method-only inference of this kind is unsound.

PUT marked idempotent

PUT is idempotent under RFC 9110, so idempotentHint=true has a method-level basis. But PUT can replace existing state, so the method alone does not justify an additive-only claim.

PATCH marked idempotent

PATCH is not generically idempotent. An individual PATCH operation may have stronger properties, but those need operation-specific evidence rather than a universal method rule.

DELETE marked idempotent

DELETE is standardized as idempotent, so the profile allows the idempotence claim. That does not make deletion non-destructive.

Applicability comes first

The checker is deliberately conditional. Before lifting a method guarantee into MCP, the HTTP method must still faithfully characterize the generated tool's requested or intended effect for that guarantee.

For example, a tool that performs GET /account but also requests a write to another store cannot inherit a read-only claim merely because one component uses GET. Likewise, when HTTP idempotence is lifted, repeated MCP calls with the same arguments must preserve equivalent operation-relevant HTTP request semantics. Different request IDs, authentication tokens, or tracing metadata do not by themselves break that condition.

The profile calls this effect-faithful translation. The checker assumes it. It does not verify it.

Sound is not the same as maximal

The primary goal is to prevent unsupported claims. A translator that intentionally underclaims can still be sound.

PROFILE_MAXIMAL is a secondary precision measure: it asks whether a sound state also expresses the strongest representation justified by the Core. MCP does not require profile maximality, and SOUND_NON_MAXIMAL is not a failure.

This distinction keeps the profile focused. It is stricter about saying too much than about saying too little.

Independent implementation witnesses

The frozen artifact also reproduced method-default mappings from three independent implementation sources and evaluated those specific mappings under the same Core. These are witnesses, not normative authorities and not whole-product verdicts.

Reproduced method-default layer Sound methods Unsupported active guarantees API7 documented defaults 5 / 5 0 Infobip verified source defaults 2 / 5 3 Azure App Service documented defaults 2 / 5 4

API7's documented defaults independently converged with the profile-maximal mapping for all five methods. In the frozen Infobip mapping, the reproduced POST, PUT, and PATCH defaults activated additive-only guarantees not justified by the method alone. In the frozen Azure mapping, POST and PUT activated additive-only guarantees, while PATCH activated both additive-only and idempotent guarantees.

Those findings are intentionally narrow. They classify the reproduced method-inference defaults under this profile, not API7, Infobip, or Azure as products.

The blind witness annex

A formal method table can still feel abstract, so the project kept a separate semantics-blind witness set. It contains 25 method-stratified operations and eight unique operation-level evidence records. The annex does not define the Core and cannot estimate prevalence.

Within that frozen set, six matched contradiction witnesses documented real POST, PUT, and PATCH operations that edit, replace, or delete existing state. Those examples make one boundary concrete: method semantics alone cannot support a universal rule that these methods are non-destructive.

The annex also contained one supported additive-only POST at the operation level. That is useful for the opposite reason. It shows that a stronger claim may sometimes be justified, but only by additional evidence about the specific operation. The Core therefore leaves proof-carrying, operation-specific exceptions experimental rather than weakening the method-level rule for everyone.

What the project established

The source method sets a bounded semantic budget. For an effect-faithful translation, method-derived MCP annotations are sound when their active guarantees stay inside that budget. The executable profile makes that boundary deterministic and testable instead of leaving it as an informal mapping convention.

The broader intuition is simple: translating an interface should not silently strengthen what the source can support. In this project that intuition is proven only for the declared five-method HTTP to MCP profile. It is not presented as a universal translation theory.

What it does not establish

  • It does not verify that a real wrapper is effect-faithful.
  • It does not certify runtime behavior, tool safety, server honesty, HTTP compliance, or MCP server trustworthiness.
  • It does not validate explicit operation-specific annotations or evidence.
  • It does not measure Internet prevalence or ecosystem-wide converter quality.
  • It does not classify entire vendor products from the reproduced witness mappings.
  • It does not cover every HTTP method or custom operation.
  • It is not an official MCP, IETF, OpenAPI, vendor, or standards-body profile.
  • It does not require translators to be profile-maximal.

Freeze and reproducibility

Version 0.2.1 is an experimental draft for public review. It clarified applicability, status, framing, packaging, and machine-readable metadata without changing the v0.2.0 decision model or any substantive result.

  • The byte-frozen v0.2.0 object passes 32 of 32 baseline tests.
  • V0.2.1 strict typecheck, build, deterministic generation, and all 36 tests pass in the frozen record.
  • The 40-vector oracle and translator artifacts regenerate without byte changes.
  • The empirical machine artifact and sampler hashes verify exactly.
  • A clean extraction can install from the lockfile and run pnpm verify without an upstream checkout or sibling project.
  • Runtime dependency count is zero. TypeScript 5.9.3 is the sole pinned development dependency.
