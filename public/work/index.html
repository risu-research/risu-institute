Research program

From meaning to consequence.

RISU studies how machine-readable claims acquire operational force as they move from semantic identity, through evidence and reliance, to action. Each project remains bounded to its own formal and empirical record.

Research disciplineClaims are scoped before they are generalized. Formal consequence, empirical observation, source preservation, and operative evidence remain separate unless a specific artifact establishes the link.

Native++ v0.2

Admitting platform-native attestations into a frozen consequence-evidence substrate.

Primary result: PASS, narrow claim only. A verified GitHub release attestation discharged four precommitted release and asset-binding claims without adding any new generic consequence or evidence machinery.

Question

A consequence-assurance system can end up reconstructing facts that the platform already exposes through a stronger native proof. Native++ asked whether the existing frozen substrate could recognize that situation and become smaller rather than build another verification path.

If a platform already exposes a mature native proof primitive, can the consequence-evidence substrate consume that proof under an explicit trust policy while preserving the claim boundary and leaving the generic core unchanged?

Why the experiment matters

The important comparison is not RISU versus GitHub verification. GitHub already performs the native cryptographic verification. The architectural question is whether a higher-level consequence system knows when not to duplicate mature platform verification.

Earlier reconstruction path Git ref resolution + release and API observations + platform digest information + downloaded bytes + pagination and completeness logic → consequence-relevant bindings Native++ path for the tested facts pinned native verifier → verified signed release statement → audited schema admission → existing typed evidence → unchanged generic kernel

The second path is valid only for facts that the signed statement actually establishes. Anything outside that signed scope remains separately obligated.

Experimental boundary

The fresh primary used GitHub CLI release v2.100.0. Before the signed attestation was consumed, the experiment fixed the expected release commit and selected asset digest. The signed statement was then admitted only through a sealed binding with explicit schema rules.

Admission discipline

Cryptographic validity and semantic admission were treated as different decisions. The native verifier established the signed statement. The local binding then checked that the statement was one of the explicitly audited release predicate versions and that the decoded DSSE payload exactly matched the verifier-returned statement before admitting consequence-relevant facts.

Unsupported future predicate versions fail closed rather than being guessed into compatibility.

Precommitted generic constraint

The experiment was not allowed to make GitHub look easy by inventing a new generic abstraction after seeing the result. All five generic expansion counts had to remain zero.

generic core changes 0 new contract judgment kinds 0 new provider I/O verbs 0 new proof-algebra operations 0 new evidence-atom kinds 0

Primary data

The verified in-toto statement contained 23 subjects. It included exactly one release URI subject and exactly one selected target-asset subject matching the precommitted target. The decoded DSSE payload and the statement returned by the verifier were independently checked for exact JSON equality.

Negative controls

A positive path is not useful if nearby invalid evidence also passes. Native++ therefore required two rejection controls.

One-byte mutation Authentic target asset changed at exactly one byte Byte length preserved Result: REJECTED Wrong release Authentic v2.100.0 bytes checked against v2.96.0 Result: REJECTED

The mutated object had SHA-256 a99e439468a59d4d2dcbea681960e5df2b112d23d71c2c816e18663f6b658086. Both controls passed by being rejected as required.

Supported conclusion

When a platform-native signed proof already binds the exact facts required by a consequence claim, the frozen substrate can admit that proof under an explicit trust and binding policy and avoid redundantly reconstructing those same facts through weaker evidence planes.

This is an evidence-topology collapse signal. It shows that the architecture can shrink around stronger native evidence while keeping the generic consequence/evidence vocabulary fixed.

What this does not establish

  • cross-provider semantic-labor amortization;
  • trivial provider-specific binding work;
  • superiority over GitHub's native verifier;
  • availability or temporal-delivery guarantees;
  • namespace-wide uniqueness;
  • payment or economic finality;
  • correctness of arbitrary consequences;
  • that all consequences reduce to attestations;
  • elimination of the binding trusted-computing base;
  • commercial superiority over a strong bespoke implementation.

Why the failed runs remain in the record

The successful primary came after two scientifically useful failures. Run 33805476200 stopped before primary observation because archive identity and executable identity had been conflated. Run 33806977992 reached its then-primary target and exposed a stale release-predicate schema assumption after cryptographic verification. That consumed target was not reused. Native++ v0.2 selected a fresh primary instead.

The failures are retained as failures. They explain why v0.2 separates verifier identity, schema admission, and consequence evidence instead of silently treating successful signature verification as sufficient.
