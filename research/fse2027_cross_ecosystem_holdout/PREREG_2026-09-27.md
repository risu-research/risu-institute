# FSE 2027 Cross-Ecosystem Holdout — Frozen Protocol

Frozen before candidate discovery/replay on 2026-09-27 UTC.

## Purpose
Test whether the code–contract pairing phenomenon observed in Dafny survives an outcome-independent holdout in non-Dafny verification ecosystems. This is an external-validity holdout, not a prevalence study.

## Strict stage separation
1. PRE-REGISTRATION: freeze repositories, lexical/structural rules, fallback ladder, eligibility, ranking, replay rules, and stopping rules.
2. DISCOVERY: enumerate candidates without running counterfactual hybrids and without using desired verifier outcomes for selection.
3. ADJUDICATION: decide eligibility and deterministic priority from source/diff/dependency evidence only.
4. REPLAY: execute historical endpoints first, then every mandatory four-way replay selected by the frozen rule.
5. INTERPRETATION: only after replay results are frozen may outcomes be interpreted.

No candidate may be promoted, demoted, or replaced because its replay matrix is aesthetically weak or contradicts the Dafny pattern. Infrastructure/toolchain failures are preserved distinctly from scientific verification outcomes.

## Holdout strata
Primary strata are fixed as:
- V: `verus-lang/verus` (Verus ecosystem)
- F: `FStarLang/FStar` (F* ecosystem)

Previously inspected Verus PR #1823 is contamination-known and excluded from holdout selection, although it may be reported separately as a pre-holdout near miss. No known F* candidate is preselected.

## Discovery window
All first-parent/non-root commits reachable from the default branch with commit date >= 2024-01-01 and <= the freeze commit time are eligible for discovery. Merge commits are retained only if the first-parent patch itself contains qualifying source changes. Historical commits outside this window are not used to rescue a failed stratum.

## Source frames
### Verus
Primary files: `*.rs` under the repository, excluding generated/vendor/build/output directories when obvious from path.
Contract lexemes: `requires`, `ensures`, `invariant`, `decreases`, `recommends`.

### F*
Primary files: `*.fst` and `*.fsti`, excluding generated/vendor/build/output directories when obvious from path.
Contract lexemes: `requires`, `ensures`, `decreases`.
Interface/implementation pairing of a same-basename `.fsti`/`.fst` is allowed only in fallback tier C below.

## Eligibility ladder, applied in order within each stratum
A candidate is adjudicated without hybrid execution.

Tier A — same callable / same definition:
- one historical commit changes an explicit contract lexeme and executable body lines inside the same named callable/definition;
- old and new endpoint text are preserved;
- the two dimensions are mechanically separable without inventing semantics.

Tier B — same file, named linkage:
- explicit contract change and executable-body change occur in the same source file and are linked to the same named callable/specification target;
- mechanical separation is still possible and unrelated source can remain fixed.

Tier C — interface/implementation pair (F* only):
- a same-basename `.fsti` contract/signature and `.fst` executable implementation change in the same commit for the same exported definition;
- both sides can be cross-combined mechanically while keeping all unrelated files fixed.

Tier D — narrow semantic specification function:
- only if A–C produce no eligible candidate in a stratum;
- a specification function/predicate and executable body change in one repair and are mechanically separable.
- This tier must be labeled weaker than literal contract migration.

A stratum stops at the first tier containing at least one eligible candidate; lower tiers are not searched to improve the outcome.

## Exclusions
Exclude candidates when any of the following is true before replay:
- proof-only edit with no executable-body change;
- test-only edit;
- formatting/comment/generated-only change;
- contract strengthening/weakening without body change;
- body change without contract/spec change;
- hybrid construction would require semantic invention rather than mechanical old/new substitution;
- endpoint source is unavailable;
- toolchain cannot be pinned sufficiently to distinguish infrastructure failure from verification failure.

## Deterministic priority within the first nonempty tier
Sort eligible candidates by the tuple:
1. number of changed source files participating in the candidate (ascending),
2. total changed nonblank semantic lines in the isolated body+contract dimensions (ascending),
3. number of direct local imports/dependencies needed for the smallest faithful verification target (ascending where mechanically measurable; unknown sorts after known),
4. commit timestamp ascending,
5. commit SHA lexicographically ascending.

The first candidate is MANDATORY REPLAY. If it is an infrastructure/toolchain failure before any scientific matrix can be obtained, retain it and proceed to the next candidate under the same frozen ordering. Do not skip a scientifically valid but inconvenient matrix.

## Replay design
For the mandatory candidate, define:
- B0S0 = old body + old contract/specification,
- B1S0 = new body + old contract/specification,
- B0S1 = old body + new contract/specification,
- B1S1 = new body + new contract/specification.

Historical endpoints are preserved byte-for-byte wherever the repository organization permits. Counterfactual cells are produced by mechanical substitution only. All four causal cells use one pinned verifier/toolchain and identical flags, with unrelated source fixed to one documented background revision when exact whole-tree endpoints would introduce unrelated changes.

Record for every cell: exit code, verifier summary/error count, exact command, toolchain version/hash where available, source hashes, and failure locus/class.

Scientific outcomes are not limited to P/P/F/P or P/F/F/P. Any matrix is retained. Endpoint non-verification is itself a result if the toolchain is valid. Infrastructure incompatibility is not converted into a scientific FAIL.

## Endpoint/toolchain rule
Attempt in this order without inspecting hybrid outcomes:
1. repository-declared historical/revision-local toolchain if recoverable;
2. toolchain pinned by CI/config nearest the candidate commit;
3. current repository-supported toolchain only if it verifies/compiles both untouched endpoint targets sufficiently for a causal replay.

If none works after two materially different installation/build strategies, mark the candidate INFRA_BLOCKED and move to the next frozen candidate. Maximum three infrastructure strategies per candidate; no source edits solely to force compatibility.

## Stopping rule
Per stratum, stop when either:
- one mandatory candidate yields a complete four-cell scientific replay, or
- the first five eligible candidates in the first nonempty tier are all INFRA_BLOCKED, or
- no eligible candidate exists after A–D.

Run both strata independently. Success in Verus does not cancel F*, and failure in one does not change the other's rules.

## Claim boundary fixed in advance
A successful non-Dafny replay supports only cross-ecosystem existence/replication under the tested stratum; it does not estimate frequency or establish all-tool generality. A null/blocked holdout narrows external-validity claims and is preserved rather than replaced by post-hoc ecosystem shopping.
